# Small Wedding Concierge CRM

> 스몰웨딩 식당만 전문적으로 추천해주는 상담 회사(Concierge)를 위한 CRM. Salesforce 사용자는 **상담사**이며, 예비부부(고객)는 Salesforce를 사용하지 않는다. 접수는 웹폼/이메일/전화 등 여러 채널을 **표준 Lead**로 통합하고, 장소가 확정되면 **표준 Opportunity 파이프라인**(드레스→메이크업→...→준비완료)으로 자연스럽게 이어지도록 설계했다.

## 0. 배포 대상 org

이 프로젝트는 처음에 기존 "AFDX Agentforce Testdrive" 템플릿 org(`agentforce`, Coral Cloud Resort 데모가 이미 들어있는 공유 org)에서 개발되었으나, **실제 스몰웨딩 컨시어지 업체가 쓸 전용 org**로 완전히 이전했다.

- 전용 org 별칭: `wedding-concierge` (신규 Developer Edition, 인스턴스 `orgfarm-807cf85d58-dev-ed.develop.my.salesforce.com`)
- 커스텀 도메인: `smallweddingconcierge-dev-ed.develop.my.salesforce.com` (Setup > My Domain에서 사용자가 직접 등록/배포)
- 프로젝트 기본 target-org로 설정됨(`sf config set target-org=wedding-concierge`)
- 전용 Developer Edition으로 옮겼지만 원본 템플릿의 Apex·Flow와 표준 샘플 데이터 일부는 남아 있다. 포트폴리오 저장소와 검증 범위는 직접 만든 Concierge CRM 컴포넌트로 한정한다.
- `aiAuthoringBundles/Local_Info_Agent`는 이 신규 org에서 "Not available for deploy for this organization"으로 배포 불가 확인(Agentforce Agent 빌더 관련 기능이 아직 활성화되지 않음) — Concierge CRM 핵심 기능과는 무관해 제외하고 진행
- 전용 Lightning App **`Wedding Concierge`**를 새로 만들어 App Launcher에 노출(`force-app/main/default/applications/Wedding_Concierge.app-meta.xml`) — 홈, Lead, Venue, Venue Type, Recommendation, Opportunity, Contact, Account 탭을 한 앱에 모아, 상담사가 여러 탭을 따로 찾아다닐 필요 없게 했다. `Concierge_CRM_Perms` 권한 세트의 `applicationVisibilities`로 노출.

## 1. 문제 정의

표면적 문제("서울에서 40명 규모 스몰웨딩 식당을 찾기 어렵다")를 폐기하고 진짜 문제로 재정의했다:

> **스몰웨딩은 정답이 없는 결혼식이다.** 예비부부는 무엇을 먼저 결정해야 할지, 자신에게 뭐가 정말 중요한지조차 정리되지 않은 채 장소·드레스·메이크업·사진·답례품 등 수십 개의 선택을 동시에 마주한다.

정보 부족이 아니라 **판단 기준의 부재**와 **의사결정 순서의 혼란**이 핵심이며, 이번 스코프는 그중 "장소 결정" 단계 하나만 완전히 구현하고 나머지는 Opportunity Stage에 이름만 존재하는 **로드맵(Beachhead 전략)**으로 남겼다.

## 2. 두 페르소나

| | 문제 | 니즈 | Salesforce 사용 여부 |
|---|---|---|---|
| **예비부부(신부)** | 시간 없고 우선순위 정리 안 됨 | 조건에 맞는 걸 알아서 골라줬으면 함 | ❌ 사용 안 함(이메일로만 결과 수신) |
| **웨딩 컨시어지 상담사** | 신부마다 다른 조건을 매번 수기 대조, 이력 관리 안 됨 | 문의가 들어오면 즉시 근거 있는 추천을 제시하고 기록을 남기고 싶음 | ✅ 유일한 Salesforce 사용자 |

Salesforce는 소비자 앱이 아니라 **여러 고객을 이력과 함께 반복 가능한 프로세스로 응대하는 B2B 업무 툴**이라는 점이 "왜 Salesforce로 만드는가"에 대한 답이다.

## 3. 전체 흐름

```
신부 문의 (웹폼 / 이메일 / 전화)
    ↓
Lead 자동/수동 생성 (Web-to-Lead 또는 상담사 수동 입력)
    ↓
Lead Assignment Rule → 상담사에게 배정
    ↓
상담사가 Lead 검토, 필요시 전화로 조건 재확인
    ↓
상담사가 Screen Flow("Generate Recommendation") 실행
    ↓
Flow: 조건 확인/보완 → Lead 업데이트
    → 40인 이상 수용 가능한 Venue 조회
    → 이 Lead의 예산·중요도 가중치로 재계산(PersonalizedScore)
    → TOP3 산출 → Recommendation__c 3건 생성
    → 신부에게 추천 이메일 자동 발송
    ↓
신부가 Experience Cloud 추천 페이지에서 확정/답사/재추천 선택
    ↓
Lead 상태 변경 + 후속 Task 생성, 확정 시 결제 안내 이메일 발송
    ↓
상담사가 패키지 전환 Flow 실행 → Contact/Account/Opportunity 생성
    ↓
선택 장소 자동 연결, 패키지별 Record Type 및 Stage = "장소 확정"
    ↓
(로드맵) 드레스 확정 → 메이크업 확정 → 사진·스냅 확정 → 답례품 확정 → 준비 완료
```

핵심 설계 원칙: **접수는 자동화하되, 판단(Screen Flow 실행)은 항상 상담사가 트리거한다.** 웹폼으로 들어온 1차 정보를 상담사가 검증 없이 그대로 흘려보내면 컨시어지 서비스의 핵심 가치(사람이 한 번 더 검증한다는 신뢰)가 사라지기 때문이다.

## 4. 오브젝트 모델

### Lead (표준 오브젝트 + 커스텀 필드 15개)

| 필드 | 타입 | 용도 |
|---|---|---|
| `GuestCount__c` | Number | 하객 수 |
| `BudgetPerPerson__c` | Currency | 1인당 예산 |
| `FoodPriority__c` / `ParkingPriority__c` / `TransitPriority__c` | Number(1~5) | 항목별 중요도. **Picklist가 아니라 Number**로 만들고, Web-to-Lead HTML의 `<select>` 옵션 텍스트만 자연어로 바꿔치기했다 — Flow 계산식(`/5`)이 별도 변환 없이 그대로 동작하게 하기 위함 |
| `PreferredDistrict__c` | Text | 희망 지역(선택) |
| `WeddingDate__c` | Date | 예상 예식일(선택) |
| `ConsultationNotes__c` | Long Text | 상담 메모(자유 텍스트) |

### VenueType__c (마스터 데이터 4건)

레스토랑/웨딩홀/카페/야외. `Pros__c`/`Cons__c`/`BestFor__c`. 새로 조사하지 않고 기획 단계에서 이미 정리된 표를 그대로 마스터 데이터화했다.

### Venue__c (전면 재설계)

| 필드 | 타입 | 비고 |
|---|---|---|
| `MaxCapacity__c` | Number | 최대 수용인원 |
| `FoodRating__c` | Number(2,1) | 음식 평점(0~5) |
| `ReviewCount__c` | Number | 리뷰 수 |
| `PricePerPerson__c` | Currency | 1인당 예상 비용 |
| `ParkingSlots__c` | Number | 주차 가능 대수(정보없음이면 0) |
| `ParkingFee__c` | Currency | 주차비(0=무료) |
| `StationWalkMin__c` | Number | 최인접역 도보(분) |
| `PrivateRoom__c` | Checkbox | 독립공간 여부 |
| `District__c` / `Address__c` | Text | 지역/주소 |
| `VenueType__c` | Lookup(VenueType__c) | 장소 유형 |
| `IsEligible__c` | Formula(Checkbox) | `MaxCapacity__c >= 40` — 게이트 |
| `MatchScore__c` | Formula(Number) | Venue 고유의 절대 점수(가격30+음식25+주차25+교통20, 만점100). 특정 신부와 무관한 고정값 |

기존(이전 피봇)의 `Capacity__c`/`Food_Rating__c`/`Has_Parking__c`/`Price_Per_Person__c`/`Transit_Minutes__c`/`Score__c`/`Meets_Capacity__c` 필드와 15건이었던 관리자 화면용 List View는 이번 스펙에 맞춰 **전부 삭제 후 재생성**했다(기존 데이터는 샘플/픽션이었고 이번엔 실제 조사 데이터로 교체하는 시점이라 데이터 손실 부담이 없었음).

### Recommendation__c (Lead 기반, 범용 확장 구조로 재설계)

| 필드 | 용도 |
|---|---|
| `Lead__c` | 이 추천이 어느 상담 건에서 나왔는지 |
| `Venue__c` / `VenueNameSnapshot__c` | 추천된 식당. Snapshot은 Venue가 나중에 변경/삭제돼도 추천 당시 이름을 남기기 위함 |
| `MatchScore__c` | 이 Lead의 조건을 반영해 **Flow 실행 시점에 재계산된** 개인화 점수(PersonalizedScore) — Venue의 고정 `MatchScore__c`와는 다른 값 |
| `Rank__c` | 1~3위 |
| `ReasonText__c` | Flow Formula로 생성한 추천 근거 문장 |
| `BudgetDiff__c` | 예산 대비 차액(양수=저렴, 음수=초과) |
| `ProsSummary__c` / `ConsSummary__c` | VenueType의 장단점을 복사 |
| `RecommendationType__c` | Picklist(장소/드레스/메이크업/사진). **이번 스코프는 "장소"만 실제 로직 존재**, 나머지는 향후 확장을 위해 값만 미리 등록 |
| `RelatedRecordId__c` | 향후 드레스업체 등 다른 오브젝트가 생기면 그 레코드 Id를 저장할 범용 필드 |

### Opportunity (표준 오브젝트, 전용 Record Type/Business Process 분리)

이 org에는 이미 다른 데모(Coral Cloud Resort)용 Opportunity 32건이 표준 Sales Process로 존재했다. **기존 Stage 값을 지우지 않고**, 새 Record Type `Wedding_Concierge`와 전용 Business Process를 만들어 완전히 분리했다:

- `ConfirmedVenue__c`(Lookup, Venue__c) 필드 추가
- `StageName` StandardValueSet에 기존 10개 표준 값(Prospecting~Closed Lost)은 그대로 두고, 웨딩 전용 6단계를 추가: 장소 확정(20%) → 드레스 확정(40%) → 메이크업 확정(55%) → 사진·스냅 확정(70%) → 답례품 확정(85%) → 준비 완료(100%, Closed Won)
- Business Process `Wedding_Concierge`가 이 6개 값만 사용하도록 제한
- Record Type `Wedding_Concierge`가 이 Business Process를 사용
- Path Assistant를 이 Record Type 전용으로 설정, "장소 확정" 단계의 Key Field로 `ConfirmedVenue__c` 노출

이번 스코프는 **"장소 확정"만 실제 동작**하고, 나머지 5단계는 Path에 이름과 안내 문구만 존재하는 로드맵이다.

## 5. Screen Flow — `Wedding_Concierge_Recommendation`

Lead 레코드 기준으로 실행되는 단일 Screen Flow(조건 입력~이메일 발송까지 하나로 통합 — Subflow로 쪼개는 것보다 이 규모에서는 관리가 쉽다는 판단).

```
Get_Lead (recordId로 조회)
  ↓
Screen: 상담 조건 확인 (하객수/예산/지역/중요도3개/메모, Lead 값이 기본값으로 채워지고 상담사가 재조정 가능)
  ↓
Update_Lead (화면에서 수정한 값 반영)
  ↓
Get_Venues (IsEligible__c = true인 Venue 전체 조회)
  ↓
Loop_Venues:
  Get_VenueType (Venue.VenueType__c로 Pros/Cons 조회)
  → Formula로 항목별 점수 계산 → PersonalizedScore
  → 임시 Recommendation__c 레코드(미저장)를 만들어 컬렉션에 추가
  ↓
Sort (컬렉션을 PersonalizedScore 내림차순 정렬 — Collection Sort, Winter'23+ 방식)
  ↓
Loop_Top3 (정렬된 컬렉션을 순회하며 카운터로 상위 3개만 Rank 부여 + 이메일 본문 누적)
  ↓
Create_Recommendations (상위 3건만 실제 DML)
  ↓
Send Email (Core Action) → 신부에게 발송
  ↓
Screen: 완료 안내
```

### 점수 계산 (2단계 구조)

**1단계 — Venue 고유의 절대 점수**(`Venue__c.MatchScore__c`, Formula, 신부와 무관하게 고정)

**2단계 — 이 Lead의 우선순위를 반영한 개인화 재계산**(Flow 실행 시점, Formula 리소스):

```
FoodElementScore     = (FoodRating__c / 5) * 100
ParkingElementScore  = MIN(100, ParkingSlots__c / 30 * 80) + IF(ParkingFee__c = 0, 20, 0)
TransitElementScore  = MAX(0, 100 - StationWalkMin__c * 10)
BudgetFitScore       = MAX(0, 100 - ABS(PricePerPerson__c - 예산) / 예산 * 100)

PersonalizedScore = (FoodElementScore * 음식중요도
                   + ParkingElementScore * 주차중요도
                   + TransitElementScore * 교통중요도
                   + BudgetFitScore * 5)
                   / (음식중요도 + 주차중요도 + 교통중요도 + 5)
```

같은 Venue라도 신부 A(음식 중요도 5)와 신부 B(음식 중요도 2, 주차 중요도 5)는 서로 다른 순위를 받는다 — 이게 "왜 컨시어지가 매번 다시 계산해야 하는가"의 실제 근거다.

### "상위 3개 추출"을 Flow에서 구현하는 법

Flow에는 "Top N" 기능이 없다. Sort 후 카운터 변수(`var_Counter`)를 Loop마다 1씩 증가시키고, Decision(`var_Counter <= 3`)으로 상위 3개만 Rank를 부여하고 결과 컬렉션에 추가한다. 나머지는 그냥 통과시킨다(진짜 "break"가 아니라 "3개 이후엔 아무 일도 안 하고 통과"하는 방식 — Flow Loop는 중간에 완전히 빠져나올 수 없다).

### 이메일 본문 조립

Recommendation 3건을 하나의 이메일에 담기 위해, 별도 Email Template을 만들지 않고 **Flow 안에서 Long Text 변수(`var_EmailBody`)에 문자열을 계속 이어붙이는 방식**을 택했다(Formula 리소스가 자기 자신이 참조하는 변수의 "현재 값"을 매번 다시 읽어 재계산하는 특성을 이용 — `fx_AppendedEmailBody = var_EmailBody & ...` 를 매 Loop 반복마다 `var_EmailBody`에 재할당). Send Email Core Action(`emailSimple`)의 `emailBody`/`emailSubject`/`emailAddresses` 파라미터에 직접 전달한다.

## 6. Web-to-Lead

Setup 마법사를 쓰지 않고, org의 Organization Id와 커스텀 필드 Id(Tooling API로 직접 조회)를 이용해 HTML을 직접 작성했다: [`web-to-lead/wedding-inquiry-form.html`](../web-to-lead/wedding-inquiry-form.html).

- 표준 필드는 `first_name`/`last_name`/`email`/`phone` 같은 표준 이름을 쓰지만, **커스텀 필드는 API 이름이 아니라 필드 Id(`00N...`)를 `name`으로 써야 한다** — Web-to-Lead의 오래된 제약.
- `company`는 표준 Lead 필수 필드지만 개인 고객 시나리오라 화면에 노출하지 않고 hidden input으로 고정값("개인 고객") 채움.
- `lead_source`도 hidden으로 "Web-미니웨딩폼" 고정 — 이후 Convert해도 값이 승계되어 유입 채널 분석에 활용 가능.
- 우선순위 3개 필드는 Number 타입이지만, HTML의 `<select>` 옵션 텍스트는 자연어 문구(예: "하객 만족의 핵심이에요")로 채워서, 신부에게는 자연어로 보이고 시스템에는 숫자(1~5)로 저장되게 분리했다.

**사용자가 직접 확인해야 하는 것**: Setup > Web-to-Lead에서 "웹-투-리드 사용" 체크박스가 켜져 있는지(API로 확인/변경이 마땅치 않음), 그리고 이 HTML 파일을 실제 브라우저로 열어 제출 테스트(테스트는 몇 번으로 제한 — 시간당 제출 제한 있음).

## 7. Lead Assignment Rule

`Concierge_Assignment` 규칙 하나만 생성(1인 컨시어지 시나리오라 "모두 나에게 배정"). 조건은 `Lead.CreatedDate > 1/1/1900`(항상 참이 되는 조건으로 전체 매치).

| Opportunity Stage 6단계 + Business Process + Record Type + Path | ✅ (기존 Coral Cloud 데모 데이터는 건드리지 않음) |
| VenueType__c 마스터 데이터 4건 | ✅ |
| Venue__c 재설계(게이트+절대점수 Formula) | ✅ |
| Venue 데이터 입력 | ✅ 총 160건. 공식 페이지를 참고해 정리한 100건과 추천 로직 검증용 합성 데이터 60건. 실제 데이터의 가격·평점·주차·리뷰수에는 미확인 값이 남아 있어 운영 데이터로 간주하지 않음 |
| Recommendation__c 재설계(범용 확장 구조) | ✅ |
| Screen Flow(조건입력→개인화 점수→TOP3→이메일) | ✅ 실제 브라우저 종단간 검증. 점수는 0~100 정규화, 160건 중 현재 기본 게이트 통과 61건 확인 |
| Lead → Opportunity Convert 연동 | ✅ Apex와 Flow로 선택 장소·패키지별 Record Type·초기 Stage 연결 |
| 드레스/메이크업 등 다음 Stage 실제 로직 | 로드맵. Path에 이름만 존재 |

## 9. 막힌 점 / 배운 점

- **StandardValueSet(OpportunityStage)을 통째로 교체하면 기존 데이터가 위험하다.** 이 org에 이미 다른 데모용 Opportunity 32건이 표준 Stage로 존재해서,가장 먼저 `SELECT COUNT(Id), StageName FROM Opportunity GROUP BY StageName`으로 기존 값을 확인한 뒤, 기존 10개 값은 유지하고 새 6개 값만 추가했다. 별도 Business Process + Record Type + Path로 완전히 분리해 서로 간섭하지 않게 했다.
- Opportunity `BusinessProcess`는 `<default>true</default>`를 허용하지 않는다("Cannot specify a default on: Opportunity") — Lead/Case의 Business Process와 다른 제약.
- Stage 이름에 `/`(슬래시)가 들어가면 BusinessProcess가 이를 찾지 못한다(`사진/스냅 확정` → `사진·스냅 확정`으로 변경).
- `Recommendation__c.Lead__c` 같은 Lead를 향한 Lookup은 **필수(required) + Cascade delete 조합이 불가능**하다("Cannot add a lookup relationship child with cascade or restrict options to Lead"). Lead는 선택 Lookup + 기본 delete constraint로 둬야 한다.
- Picklist 필드의 `valueSet`에서 `restrictedToValueSet`을 넣으면 파싱 에러가 난다 — 커스텀 `valueSetDefinition`을 쓸 때는 이 태그 자체를 생략해야 한다.
- **Flow 메타데이터는 자식 요소들이 태그 이름 알파벳 순으로 그룹핑되어 있어야 한다.** 실행 순서는 `connector`/`targetReference`로 결정되므로 XML 문서 안에서의 물리적 위치와 무관하지만, 같은 태그(`recordLookups`, `assignments` 등)는 서로 떨어져 있으면 안 되고 전부 모아놔야 한다(예: `Get_Lead`와 `Get_Venues`가 다른 `recordLookups` 두 곳에 나뉘어 있으면 "Element recordLookups is duplicated" 에러).
- **Flow의 "Collection Sort"는 API 상 독립된 `sorts` 엘리먼트가 아니라 `collectionProcessors`(`collectionProcessorType = SortCollectionProcessor`)다.** 정렬 기준 필드명도 `field`가 아니라 `sortField`.
- **Formula 리소스의 문자열 안에 실제 줄바꿈 문자를 넣으면 배포 시 "Syntax error"가 난다.** 이메일 본문처럼 여러 줄이 필요한 텍스트는 이번 스코프에서는 구분자(예: `" - "`, `" *** "`)로 대체했고, 진짜 줄바꿈이 필요하면 별도 검증이 더 필요하다(향후 과제로 남김).
- Screen Flow는 Apex의 `Flow.Interview.start()`로 헤드리스 실행이 안 된다("Start can't be called on a flow with the process type Screen Flow") — 브라우저(`/flow/<FlowApiName>?recordId=<Id>`)로만 실제 실행/검증이 가능하다.
- **Flow 타입 Quick Action은 표준 Page Layout의 Quick Action List/Platform Action List에 추가할 수 없다**("You can't add QuickActionType Flow to a QuickActionList"). Lightning Record Page(App Builder)에는 배치 가능하지만 이는 메타데이터로 안전하게 자동화하기엔 리스크가 있어, 이번 스코프에서는 URL 직접 접근(`/flow/Wedding_Concierge_Recommendation?recordId=...`)으로 대체했다. Quick Action 자체는 만들어뒀으니, 실제 배치는 Setup의 App Builder에서 1~2분이면 가능하다(사용자 몫으로 남김).
- Flow에서 Prompt Template을 Action으로 호출할 때(이전 피봇에서 만든 `Parse_Consultation_Notes_Flow` 및 3개 Prompt Template은 그대로 재사용 가능) 정확한 `actionType`/파라미터명은 문서화가 부실해서, org의 REST API(`/services/data/vXX.0/actions/custom/generatePromptResponse/<템플릿명>`)로 직접 조회해서 확인하는 편이 가장 빨랐다.
- Send Email Core Action은 `emailAddresses`/`emailSubject`/`emailBody`만 넣으면 메일은 발송되지만 **Activity(Task) 이력은 자동으로 안 남는다.** `recipientId`(Lead Id)와 `logEmailOnSend=true`를 명시적으로 넣어야 발송 이력이 Lead의 Activity Timeline에 기록된다.
- Naver Map은 이 환경의 웹 조회 도구에서 도메인 자체가 차단되어 있고("unable to fetch from map.naver.com"), 대안으로 시도한 카카오맵도 완전 JS-렌더링 SPA라 평점/리뷰수를 텍스트로 추출할 수 없었다 — 이런 값은 추측해서 채우지 말고 명시적으로 "미확인(0)"으로 남겨야 한다는 걸 재확인.
- **`sf org login web`은 새로 가입한 Developer Edition처럼 인증까지 시간이 걸리는 상황에서 타임아웃(`AuthTimeoutError`)이 잘 난다.** 이메일 인증까지 포함한 가입을 브라우저에서 완전히 끝내고 실제 로그인이 되는 걸 확인한 *다음에* 로그인 명령을 실행해야 성공률이 높다. 이 CLI 버전은 `org login device`(코드 입력 방식)를 지원하지 않아 `org login web`만 사용 가능했다.
- 커스텀 도메인(My Domain)을 새로 등록/배포한 org는 URL이 바뀌므로, `sf org login web`에는 **배포가 끝난 커스텀 도메인 URL**(`--instance-url`)을 써야 한다 — 프로비저닝 중인 임시 `orgfarm-*.develop.my.salesforce.com` URL로는 인증이 되긴 하지만, 도메인 배포 완료 후에는 새 도메인으로 다시 인증하는 편이 안전하다.
- org를 통째로 옮길 때 `sf project deploy start -d force-app`처럼 전체 배포를 시도하면, 원본 org에만 있던 조각들이 걸린다: 다른 org 사용자 이메일이 박힌 `AssignmentRule`(`assignedTo`), 그 org에만 존재하는 필드를 참조하는 표준 오브젝트 `Layout`(예: `CurrencyIsoCode` — 다중통화 비활성 org에는 없음), Agentforce/Einstein 기능이 아직 없는 신규 org에서 거부되는 `AiAuthoringBundle`("Not available for deploy for this organization"). 이런 org-종속 조각은 배포 대상에서 빼거나 새 org 값으로 고쳐야 한다.
- `PermissionSet.applicationVisibilities`는 `<default>` 태그를 넣으면("이 앱을 기본 앱으로") 위치 상관없이 파싱 에러가 난다 — `<visible>true</visible>`만 넣으면 된다.
- 같은 배포 안에 서로 참조하는 신규 컴포넌트(새 `CustomApplication` + 그 앱을 참조하는 `PermissionSet`)를 **한 번에 같이 배포하면, 한쪽이 실패할 때 트랜잭션 전체가 롤백**되어 먼저 성공했어야 할 컴포넌트까지 사라진다("no CustomApplication named ... found" 같은 에러가 다음 배포에서 나면 이 케이스를 의심). 의존관계가 있는 신규 컴포넌트는 먼저 것만 따로 배포해 완전히 성공시킨 뒤, 그걸 참조하는 컴포넌트를 배포하는 순서가 안전하다.
- **새 Record Type을 만들었다고 자동으로 그 Record Type이 사용자에게 보이는 게 아니다.** Permission Set에 `recordTypeVisibilities`를 명시적으로 추가해야 Lead Convert 화면 등에서 해당 Record Type(예: `Opportunity.Wedding_Concierge`)이 선택 가능해진다. `recordTypeVisibilities`도 `applicationVisibilities`와 마찬가지로 `<default>` 태그를 넣으면 파싱 에러가 나서, `<visible>true</visible>`만 사용했다.
- **★ 가장 중요한 발견: Lead Convert는 커스텀 Business Process의 Stage를 존중하지 않는다.** Opportunity의 `BusinessProcess`는 애초에 `<default>` Stage를 지정할 수 없다는 제약이 있어서(9장 참고), Lead Convert가 Opportunity를 생성할 때 우리가 만든 6단계(장소 확정 등)가 아니라 **전역 기본 Stage("Prospecting")로 떨어진다.** 상담사가 매번 수동으로 Stage를 바꿔야 하는 리스크라, `Set_Default_Wedding_Stage`라는 Record-Triggered Flow(Opportunity, Before-Save, Create 시)를 추가해 `RecordTypeId = Wedding_Concierge`이고 `StageName = 'Prospecting'`인 경우 자동으로 `'장소 확정'`으로 보정했다. 이 Flow가 없었다면 실제 시연에서 Convert 직후 Path가 엉뚱한 Stage를 가리켜서 어색했을 것.
  - 이 Before-Save Flow의 진입 조건은 `RecordType.DeveloperName`처럼 관계 필드를 참조하면 Lead Convert 트랜잭션 내부에서 `UNKNOWN_EXCEPTION`(내부 오류)이 났다. `RecordTypeId`를 리터럴 Id 값으로 직접 비교하니 해결됨 — Lead Convert처럼 여러 오브젝트를 한 트랜잭션에서 동시에 만드는 특수 DML 안에서는 Before-Save Flow의 관계 필드 참조가 불안정할 수 있다는 교훈. (단점: RecordType Id가 org마다 다르므로 이 Flow를 다른 org로 옮기면 Id를 다시 조회해서 바꿔야 한다.)
- **재실행 시 추천이 계속 쌓이는 버그를 시연 리허설 중 실제로 발견했다.** 상담사가 조건을 바꿔서 Screen Flow를 다시 실행하면(예: 처음 실행 후 우선순위를 다시 조정) 이전 Recommendation__c 3건이 그대로 남은 채 새 3건이 추가되어 계속 누적되는 구조였다. `Delete_Old_Recommendations`(Delete Records, `Lead__c = recordId` 조건)를 `Update_Lead` 다음·`Get_Venues` 이전에 추가해 매번 실행 전에 이 Lead의 기존 추천을 정리하도록 고쳤다.
  - **그런데 이 Delete Records 엘리먼트 자체가 새 버그였다: 삭제 조건에 맞는 레코드가 하나도 없으면(즉 처음 실행하는 Lead) Flow가 `FLOW_ELEMENT_ERROR`로 실패한다**("Salesforce에 삭제 기준과 일치하는 레코드가 없습니다"). Delete Records는 Get Records와 달리 매치되는 레코드가 0건이면 정상 통과가 아니라 폴트(fault)로 처리된다는 뜻. `faultConnector`를 정상 경로(`Get_Venues`)와 동일하게 연결해 "삭제할 게 없어도 그냥 진행"하도록 고쳤다.
  - 디버깅 방법: Screen Flow는 브라우저에서만 재현 가능하고 에러 메시지가 화면에 짧게만 뜨므로, Tooling API로 해당 사용자에 `TraceFlag`+`DebugLevel`을 걸어두고 재현시킨 뒤 `ApexLog`의 `FLOW_ELEMENT_ERROR` 라인에서 정확한 실패 지점(엘리먼트 이름)을 확인하는 방식이 가장 빨랐다.

## 10. 유의사항

- `web-to-lead/wedding-inquiry-form.html`의 `oid`와 필드 Id들은 **`wedding-concierge` org에 종속**된다. org를 다시 옮기면 Tooling API(`SELECT Id, DeveloperName FROM CustomField WHERE TableEnumOrId='Lead'`)로 다시 조회해서 교체해야 한다.
- 공식 페이지를 참고해 정리한 Venue 100건은 음식평점·가격·주차대수·리뷰수가 다수 미확인이라 그대로는 점수의 변별력이 낮다. 로직과 경계 조건을 검증하기 위해 `[데모]` 10건과 `[가상]` 50건을 별도로 구성했다. 고객 화면에서도 이 데이터를 식별할 수 있도록 배지를 표시하고, 카드 이미지는 실제 장소 사진이 아니라 장소 유형 참고 이미지임을 명시한다.
- Naver Map(`map.naver.com`)은 이 환경의 웹 조회 도구에서 접근 자체가 차단되어 있고, 카카오맵은 접근은 되지만 완전히 JS로 렌더링되는 페이지라 평점/리뷰수 데이터를 텍스트로 가져올 수 없었다 — 값을 추정해서 채우지 않고 0(미확인)으로 명시한 이유.
- 검증에 썼던 테스트 Lead(`test-lead@example.com`)와 그 Recommendation 레코드는 (agentforce, wedding-concierge 양쪽 org 모두) 검증 완료 후 삭제했다.

## 11. 시연 준비 상태 (채널별 접수 → Convert 검증)

시연 전 세 가지 접수 채널과 Lead Convert를 실제로 검증했다.

| 채널 | 검증 방법 | 결과 |
|---|---|---|
| 웹폼 | `web-to-lead/wedding-inquiry-form.html`과 동일한 파라미터로 실제 Web-to-Lead 엔드포인트에 HTTP POST(브라우저 없이 Node로 UTF-8 인코딩 직접 제어) | ✅ Lead 생성, 한글 필드 정상 저장, Assignment Rule로 담당자 자동 배정 확인 |
| 전화 | 상담사가 통화 중 직접 입력하는 상황을 가정해 Lead 직접 생성 | ✅ |
| 이메일 | 이메일 내용을 보고 상담사가 직접 입력하는 상황을 가정해 Lead 직접 생성(이메일 자동 파싱 기능은 이번 스코프에 없음 — 상담사가 읽고 수동 입력하는 게 설계된 흐름) | ✅ |
| Lead Convert | `Database.convertLead`로 Apex 직접 테스트 | ⚠️→✅ 처음엔 Opportunity Stage가 우리가 만든 "장소 확정"이 아니라 전역 기본값 "Prospecting"으로 떨어지는 버그 발견 → `Set_Default_Wedding_Stage` Flow 추가로 수정, 재검증 통과 |

세 채널의 데모 Lead로 Screen Flow를 반복 실행해 추천이 정확히 3건만 남는지 확인했다. 이 과정에서 두 개의 버그를 발견해 고쳤다.

1. Delete Old Recommendations를 넣기 전에는, 같은 Lead로 Screen Flow를 재실행하면 추천이 3→6→9건... 계속 쌓였다.
2. Delete Old Recommendations를 넣은 직후에는, 삭제할 기존 레코드가 하나도 없는 "첫 실행"에서 오히려 Flow가 실패했다(Delete Records 엘리먼트는 매치되는 레코드 0건이면 폴트로 처리됨). `faultConnector`를 정상 경로와 동일하게 연결해 해결.

시연 순서: Lead를 열어 상담 조건 Screen Flow 실행 → TOP 3와 이메일 발송 이력 확인 → 고객용 공개 페이지에서 확정/답사/재추천 중 하나를 선택 → Lead 상태와 후속 Task 확인 → 결제 확인 후 패키지 전환 Flow 실행 → 선택 장소, Record Type, `장소 확정` Stage가 반영된 Opportunity 확인.
